{% comment %} One row of the entry table. Used both for the rows entry_week seeds on initial render and for a fresh row appended by "+ Add row" (ties, or extra debuts beyond the seeded count). The last-week-# input carries an explicit, sequential tabindex (1, 2, 3, ... down the rows) so Tab jumps straight from one row's last-week # to the NEXT row's, for fast entry of the 85-95% typical week that's just carryovers -- "1 [Tab] 3 [Tab] [Tab] 5 [Tab] 6 ...", not a detour through that row's own position/search/wks-on/anomaly-note fields first. Every other field on the page is left with NO tabindex (the default, "0"), which the browser visits only AFTER every explicitly-numbered field -- so they're still fully keyboard-reachable (Tab keeps going after the last row), just never landed on in the middle of typing last-week numbers. Position doesn't need its own tabindex: it's pre-filled from the seeded row count and rarely needs touching. No printed_peak_position input -- the owner has never seen a peak position printed on the actual pages being transcribed, so there's nothing to type against. The model field stays (ChartEntry.printed_peak_position); this is purely a "don't render a control with nothing to fill in" call, easy to reverse if a later chart era does print it. {% endcomment %}
